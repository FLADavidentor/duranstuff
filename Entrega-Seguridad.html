3. El secreto

32 bytes aleatorios en Base64, puestos como variable de entorno en IntelliJ. La app revisa la clave al arrancar y no sigue si no sirve: 

@Bean
SecretKey jwtSecretKey() {

    String base64 = System.getenv("JWT_SECRET_BASE64");

    if (base64 == null || base64.isBlank()) {
        throw new IllegalStateException(
                "Configure la variable de entorno JWT_SECRET_BASE64");
    }

    byte[] clave = Base64.getDecoder().decode(base64);

    if (clave.length < 32) {
        throw new IllegalStateException(
                "La clave HS256 debe tener al menos 32 bytes");
    }

    return new SecretKeySpec(clave, "HmacSHA256");
}

return http

STATELESS quiere decir que no hay sesión: cada petición trae su token. El orden importa porque gana la primera regla que coincide, así que puse la de GET antes de la general: leer lo puede hacer USER, todo lo demás es sólo ADMIN.

Un cambio a propósito. La guía abre /api/auth/**. Yo abrí sólo /api/auth/login, porque el reto opcional pide que /api/auth/perfil rechace a los anónimos y con el comodín habría quedado público.

El claim roles

JwtGrantedAuthoritiesConverter roles = new JwtGrantedAuthoritiesConverter();
roles.setAuthoritiesClaimName("roles");
roles.setAuthorityPrefix("ROLE_");

El token trae "roles": ["ADMIN"]. El conversor le pega ROLE_ adelante y queda ROLE_ADMIN, que es lo que revisa hasRole("ADMIN").

5. Cómo se emite el token

JwtClaimsSet claims = JwtClaimsSet.builder()
        .issuer("nicamarket-laboratorio")
        .issuedAt(ahora)
        .expiresAt(ahora.plus(30, ChronoUnit.MINUTES))
        .subject(auth.getName())
        .claim("roles", roles)
        .build();

El AuthController le pasa usuario y contraseña al AuthenticationManager, que las compara con BCrypt. Si no cuadran, no hay token.

Reto opcional: GET /api/auth/perfil

@GetMapping("/perfil")
public Map<String, Object> perfil(Authentication auth) {

    List<String> roles = auth.getAuthorities().stream()
            .map(GrantedAuthority::getAuthority)
            .filter(a -> a.startsWith("ROLE_"))
            .map(a -> a.substring(5))
            .toList();

    return Map.of("usuario", auth.getName(), "roles", roles);
}

Sin token da 401. Con token válido:

{"usuario":"admin","roles":["ADMIN"]}

9. Preguntas de cierre

  1. ¿En qué se diferencian HTTP 401 y 403? 401 es «no sé quién sos»: falta el token o no sirve, y mandando la credencial correcta se arregla. 403 es «ya sé quién sos, pero no te toca»: el token está bien, el rol no alcanza, y repetir con el mismo token siempre va a dar lo mismo. En la práctica: productos sin token da 401, y crear un producto con el token de operador da 403.
  2. ¿Por qué no basta con leer el contenido de un JWT para confiar en él? Porque las dos primeras partes son Base64, no están cifradas: cualquiera las lee y las puede cambiar, por ejemplo poner "roles": ["ADMIN"]. Lo que da confianza es la firma, que sólo se calcula con la clave secreta y el servidor vuelve a calcular cada vez. Por eso la prueba 7, con el token alterado, da 401.
  3. ¿Qué función cumple JwtDecoder? Agarra el token de la cabecera y lo valida antes de que la petición llegue al controlador: revisa la firma con la clave y HS256, revisa que no esté vencido y entrega los claims ya verificados. Si algo falla, 401 y de ahí no pasa.
  4. ¿Qué riesgos ocasionaría publicar la clave utilizada para firmar tokens? Con HS256 la misma clave firma y verifica, así que quien la tenga se puede fabricar un token de ADMIN sin saber ninguna contraseña, y el servidor se lo acepta porque la firma es legítima. Y como los tokens no se consultan contra la base, no se pueden revocar uno por uno: habría que rotar la clave y tumbar todos de golpe. Por eso va en variable de entorno y no en el repositorio.

10. Notas

La guía está hecha para Spring Boot 3.x con Security 6. Este proyecto usa Spring Boot 4.1.1 con Security 7 y el código compiló igual. Lo único que tuve que arreglar fue /perfil: Security 7 agrega una autoridad técnica FACTOR_BEARER junto a los roles, así que filtro sólo las que empiezan con ROLE_.

Como dice la nota de la guía, aquí la misma app emite y valida los tokens para simplificar el laboratorio. En algo real convendría separar emisor y validador, guardar la clave en un gestor de secretos, validar emisor y audiencia, y usar HTTPS. CSRF se puede desactivar porque la API no usa sesiones ni cookies: la credencial va en la cabecera, y eso un sitio externo no lo puede mandar solo.
