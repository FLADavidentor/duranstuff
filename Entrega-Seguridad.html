Sobre el secreto. La clave de firma HS256 no se encuentra en este documento ni en el repositorio. Se lee de la variable de entorno JWT_SECRET_BASE64 y la aplicación se niega a iniciar si falta o si tiene menos de 32 bytes. Tampoco se incluye ningún token vigente: los tokens de las pruebas vencen a los 30 minutos y se generan en cada ejecución.

3. Configuración del secreto

El secreto se genera con 32 bytes aleatorios codificados en Base64 y se configura como variable de entorno en la configuración de ejecución de IntelliJ. La validación ocurre al construir el SecretKey: 

@Bean
SecretKey jwtSecretKey() {

    String base64 = System.getenv("JWT_SECRET_BASE64");

    if (base64 == null || base64.isBlank()) {
        throw new IllegalStateException(
                "Configure la variable de entorno JWT_SECRET_BASE64");
    }

    byte[] clave = Base64.getDecoder().decode(base64);

    if (clave.length < 32) {
        throw new IllegalStateException(
                "La clave HS256 debe tener al menos 32 bytes");
    }

    return new SecretKeySpec(clave, "HmacSHA256");
}

4. Cadena de filtros y reglas de acceso

return http
        .csrf(csrf -> csrf.disable())
        .sessionManagement(session -> session
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/login", "/api/publico/**")
                        .permitAll()
                .requestMatchers(HttpMethod.GET, "/api/productos/**")
                        .hasAnyRole("USER", "ADMIN")
                .requestMatchers("/api/productos/**")
                        .hasRole("ADMIN")
                .requestMatchers(HttpMethod.GET, "/api/categorias/**")
                        .hasAnyRole("USER", "ADMIN")
                .requestMatchers("/api/categorias/**")
                        .hasRole("ADMIN")
                .anyRequest().authenticated())
        .oauth2ResourceServer(oauth -> oauth.jwt(jwt ->
                jwt.jwtAuthenticationConverter(converter)))
        .build();

STATELESS impide que se cree una sesión HTTP: cada petición debe traer su token. El orden importa, porque gana la primera regla que coincide: la regla de GET aparece antes que la general, de modo que una consulta la puede hacer USER, mientras que cualquier otro método sobre la misma ruta exige ADMIN.

Decisión sobre /api/auth. La guía propone permitAll() sobre /api/auth/**. Aquí se abrió únicamente /api/auth/login, porque el reto opcional exige que /api/auth/perfil rechace solicitudes anónimas; con el comodín habría quedado público.

Conversión del claim roles

JwtGrantedAuthoritiesConverter roles = new JwtGrantedAuthoritiesConverter();
roles.setAuthoritiesClaimName("roles");
roles.setAuthorityPrefix("ROLE_");

El token lleva "roles": ["ADMIN"]. El conversor antepone ROLE_ para producir la autoridad ROLE_ADMIN, que es la que evalúa hasRole("ADMIN").

Reto opcional: GET /api/auth/perfil

@GetMapping("/perfil")
public Map<String, Object> perfil(Authentication auth) {

    List<String> roles = auth.getAuthorities().stream()
            .map(GrantedAuthority::getAuthority)
            .filter(a -> a.startsWith("ROLE_"))
            .map(a -> a.substring(5))
            .toList();

    return Map.of("usuario", auth.getName(), "roles", roles);
}

Sin token devuelve 401; con un token válido devuelve el subject y los roles leídos del JWT: 

{"usuario":"admin","roles":["ADMIN"]}

9. Preguntas de cierre

  1. ¿En qué se diferencian HTTP 401 y 403? 401 Unauthorized significa que el servidor no sabe quién es el solicitante: falta la credencial o no es válida. Es un problema de autenticación, y reintentar con credenciales correctas puede resolverlo. 403 Forbidden significa que el servidor sí sabe quién es, pero esa identidad no tiene permiso para la operación. Es un problema de autorización, y repetir la petición con el mismo token siempre dará el mismo resultado. En esta práctica, consultar productos sin token devuelve 401, mientras que crear un producto con el token de operador devuelve 403.
  2. ¿Por qué no basta con leer el contenido de un JWT para confiar en él? Porque las dos primeras partes del token son solamente Base64URL, no cifrado: cualquiera puede decodificarlas y también modificarlas, por ejemplo cambiando "roles": ["USER"] por ["ADMIN"]. Lo que da confianza es la tercera parte, la firma, calculada con la clave secreta. Sólo quien posee esa clave puede generar una firma válida, y el servidor la recalcula en cada petición. Por eso la prueba 7 devuelve 401: el contenido parecía correcto, pero la firma dejó de coincidir al alterar el token.
  3. ¿Qué función cumple JwtDecoder? Recibir el token que llega en la cabecera Authorization y validarlo antes de que la petición alcance cualquier controlador. Verifica la firma con la clave secreta y el algoritmo declarado (HS256), comprueba que no haya vencido según expiresAt y expone los claims ya validados. Si algo falla, la petición se rechaza con 401 y nunca llega a la lógica de negocio.
  4. ¿Qué riesgos ocasionaría publicar la clave utilizada para firmar tokens? Con HS256 la misma clave firma y verifica, de modo que quien la obtenga puede fabricar tokens válidos para cualquier usuario y cualquier rol, sin conocer ninguna contraseña. Podría emitirse un token de ADMIN y acceder a todas las operaciones protegidas; el servidor lo aceptaría porque la firma sería legítima. Además, como los tokens no se consultan contra una base, no hay forma de revocarlos uno a uno: habría que rotar la clave, lo que invalida de golpe todos los tokens emitidos. Por eso la clave se mantiene fuera del repositorio, en una variable de entorno.

10. Observaciones

La guía está escrita para Spring Boot 3.x con Spring Security 6.x. Este proyecto usa Spring Boot 4.1.1 con Spring Security 7, y el código de la guía compiló y funcionó sin cambios de API. La única corrección necesaria fue en el endpoint de perfil: Spring Security 7 agrega la autoridad técnica FACTOR_BEARER junto a los roles, por lo que se filtran únicamente las autoridades que empiezan con ROLE_ antes de responder.

Tal como advierte la nota docente, en esta práctica la misma aplicación emite y valida los tokens para simplificar el laboratorio. En un sistema real convendría separar el emisor del validador, administrar la clave con un gestor de secretos, validar emisor y audiencia, y exponer la API únicamente sobre HTTPS. La desactivación de CSRF es admisible aquí porque la API no usa sesiones ni cookies: la credencial viaja en la cabecera Authorization, que un sitio externo no puede adjuntar automáticamente.
