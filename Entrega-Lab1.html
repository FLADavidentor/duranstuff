1. Arquitectura y estructura de paquetes

La arquitectura objetivo separa responsabilidades en cuatro capas:

Cliente  →  Controller  →  Service  →  Repository  →  PostgreSQL

Ninguna clase Controller accede directamente a un Repository: toda petición pasa por su Service.

2. Capa de servicios

ProductoService concentra la lógica de negocio: resuelve la categoría a partir de su identificador, construye la entidad desde el DTO y administra las etiquetas. Depende de CategoriaService y EtiquetaService, no de sus repositorios, de modo que la búsqueda y el error "no encontrada" existen en un solo lugar. 

@Service
public class ProductoService {

    private final ProductoRepository productoRepository;
    private final CategoriaService categoriaService;
    private final EtiquetaService etiquetaService;

    public ProductoService(ProductoRepository productoRepository,
                           CategoriaService categoriaService,
                           EtiquetaService etiquetaService) {
        this.productoRepository = productoRepository;
        this.categoriaService = categoriaService;
        this.etiquetaService = etiquetaService;
    }

    public Producto guardar(ProductoRequestDTO dto) {

        Categoria categoria = categoriaService
                .buscarPorId(dto.getCategoriaId());

        Producto producto = new Producto();

        producto.setCodigo(dto.getCodigo());
        producto.setNombre(dto.getNombre());
        producto.setPrecioVenta(dto.getPrecioVenta());
        producto.setExistencia(dto.getExistencia());
        producto.setCategoria(categoria);

        return productoRepository.save(producto);
    }

    public Producto agregarEtiqueta(Integer productoId, Integer etiquetaId) {

        Producto producto = buscarPorId(productoId);
        Etiqueta etiqueta = etiquetaService.buscarPorId(etiquetaId);

        producto.getEtiquetas().add(etiqueta);

        return productoRepository.save(producto);
    }
}

Los demás servicios siguen el mismo patrón, con listar(), buscarPorId(id) y guardar(dto).

3. DTOs

El DTO define exactamente qué datos acepta la API. ProductoRequestDTO recibe categoriaId, un entero, en lugar de un objeto Categoria completo: 

@Getter
@Setter
public class ProductoRequestDTO {

    private String codigo;
    private String nombre;
    private BigDecimal precioVenta;
    private Integer existencia;
    private Integer categoriaId;
}

El controlador recibe el DTO y el servicio lo convierte en entidad. El cliente nunca envía ni el id del producto ni la categoría completa, de modo que no puede alterar campos que no le corresponden.

5. Consulta de productos por categoría

La consulta se resuelve con un método derivado de Spring Data, sin escribir SQL: 

public interface ProductoRepository extends JpaRepository<Producto, Integer> {

    List<Producto> findByCategoriaId(Integer categoriaId);

    List<Producto> findByEtiquetasId(Integer etiquetaId);
}

Spring Data interpreta el nombre del método y genera la consulta. findByCategoriaId navega de Producto a Categoria y compara su id; findByEtiquetasId atraviesa la relación Muchos a Muchos.

8. Relación Producto N ─ N Etiqueta

@ManyToMany
@JoinTable(
        name = "producto_etiqueta",
        joinColumns = @JoinColumn(name = "producto_id"),
        inverseJoinColumns = @JoinColumn(name = "etiqueta_id")
)
private Set<Etiqueta> etiquetas = new HashSet<>();

@JoinTable indica a JPA cuál es la tabla intermedia y qué columna apunta a cada lado: joinColumns al lado propietario (Producto) e inverseJoinColumns al lado inverso (Etiqueta). Se usa Set y no List porque la clave primaria compuesta no admite repeticiones.

10. Solución del reto final

Reto 1 · Eliminar la asociación Producto–Etiqueta

@DeleteMapping("/{productoId}/etiquetas/{etiquetaId}")
public Producto eliminarEtiqueta(@PathVariable Integer productoId,
                                 @PathVariable Integer etiquetaId) {
    return productoService.eliminarEtiqueta(productoId, etiquetaId);
}
public Producto eliminarEtiqueta(Integer productoId, Integer etiquetaId) {

    Producto producto = buscarPorId(productoId);
    Etiqueta etiqueta = etiquetaService.buscarPorId(etiquetaId);

    producto.getEtiquetas().remove(etiqueta);

    return productoRepository.save(producto);
}

El método modifica únicamente la colección etiquetas del producto. Al guardar, Hibernate borra la fila correspondiente de producto_etiqueta, sin tocar las tablas producto ni etiqueta. La siguiente consulta lo demuestra: se asociaron dos etiquetas al producto 1 y luego se eliminó la asociación con Oferta.

Reto 2 · Consultar productos por etiqueta

@GetMapping("/etiqueta/{etiquetaId}")
public List<Producto> listarPorEtiqueta(@PathVariable Integer etiquetaId) {
    return productoService.listarPorEtiqueta(etiquetaId);
}
public List<Producto> listarPorEtiqueta(Integer etiquetaId) {

    Etiqueta etiqueta = etiquetaService.buscarPorId(etiquetaId);

    return productoRepository.findByEtiquetasId(etiquetaId);
}

Se valida primero que la etiqueta exista, de modo que una etiqueta inexistente produzca un error claro en lugar de una lista vacía que parecería un resultado válido.

11. Comprobación de aprendizaje

  1. ¿Cuál es la función de una clase Service? Contener la lógica de negocio de la aplicación: coordinar repositorios, convertir DTOs en entidades, validar reglas y decidir qué operaciones se ejecutan. Es la capa intermedia entre el controlador, que sólo atiende HTTP, y el repositorio, que sólo accede a datos.
  2. ¿Por qué un controlador no debería contener toda la lógica de negocio? Porque su responsabilidad es traducir entre HTTP y la aplicación: recibir la petición, delegar y devolver una respuesta. Si además contuviera las reglas, esas reglas quedarían atadas a la web y no podrían reutilizarse desde otro punto de entrada, el código sería más difícil de probar y una misma lógica terminaría duplicada en varios endpoints.
  3. ¿Qué es un DTO? Un objeto de transferencia de datos: una clase simple que define exactamente qué información entra o sale de la API, independiente del modelo persistente. En esta práctica, ProductoRequestDTO describe el cuerpo que acepta la creación y la actualización de productos.
  4. ¿Qué diferencia existe entre un DTO y una entidad JPA? La entidad está anotada con @Entity, corresponde a una tabla y la administra el contexto de persistencia de Hibernate. El DTO no se mapea a ninguna tabla ni lo administra JPA: existe solamente para transportar datos. Separarlos permite que el modelo de la base cambie sin alterar el contrato de la API, y evita exponer campos internos.
  5. ¿Qué ventaja tiene recibir categoriaId en lugar de una entidad Categoria completa? El cliente envía sólo el dato necesario y el servidor resuelve la categoría real contra la base, verificando que exista. Si se recibiera la entidad completa, el cliente podría enviar un nombre distinto del almacenado y modificar la categoría sin querer, o enviar un identificador inexistente que fallaría más tarde. Además, el cuerpo de la petición es más simple.
  6. ¿Qué relación representan @OneToMany y @ManyToOne? Una relación Uno a Muchos vista desde cada extremo. @ManyToOne en Producto indica que muchos productos pertenecen a una categoría; @OneToMany(mappedBy = "categoria") en Categoria expresa el mismo vínculo en sentido inverso. mappedBy señala que el lado propietario es Producto.
  7. ¿Dónde se almacena la clave foránea en la relación Categoria–Producto? En la tabla producto, en la columna categoria_id, que referencia categoria(id). La clave foránea siempre reside en el lado "muchos", que es el lado propietario de la relación.
  8. ¿Qué representa @ManyToMany? Una relación de muchos a muchos: un producto puede tener varias etiquetas y una etiqueta puede aplicarse a varios productos. Ninguna de las dos tablas puede guardar la referencia por sí sola, por lo que la relación se materializa en una tabla intermedia.
  9. ¿Cuál es la función de @JoinTable? Describir esa tabla intermedia: su nombre y las columnas que apuntan a cada lado. joinColumns define la columna de la entidad propietaria (producto_id) e inverseJoinColumns la del otro extremo (etiqueta_id).
  10. ¿Por qué se necesita la tabla producto_etiqueta? Porque en una relación Muchos a Muchos una columna no basta: un producto tendría que guardar varias etiquetas y cada etiqueta varios productos, y una columna almacena un solo valor. La tabla intermedia guarda un par (producto_id, etiqueta_id) por cada asociación, y su clave primaria compuesta impide duplicados.
  11. ¿Qué responsabilidad corresponde al Repository? Únicamente el acceso a datos: guardar, buscar, eliminar y ejecutar consultas. Al extender JpaRepository hereda las operaciones básicas, y los métodos derivados como findByCategoriaId se generan a partir de su nombre. No contiene reglas de negocio.
  12. Explique el flujo: Cliente → Controller → Service → Repository → PostgreSQL. El cliente envía una petición HTTP, por ejemplo POST /api/productos con un JSON. El Controller la recibe, Spring convierte el cuerpo en un ProductoRequestDTO y delega en el servicio. El Service aplica la lógica: busca la categoría por su identificador, construye la entidad Producto y la envía a guardar. El Repository traduce esa operación mediante Hibernate a una sentencia SQL. PostgreSQL la ejecuta y devuelve la fila. El resultado regresa por el mismo camino hasta convertirse en la respuesta JSON que recibe el cliente.

12. Conclusión

El laboratorio permitió reorganizar la API en capas con responsabilidades separadas. Los controladores quedaron reducidos a atender HTTP, los servicios concentran la lógica de negocio y los repositorios se limitan al acceso a datos, de modo que cada clase tiene una sola razón para cambiar. Los DTOs definieron el contrato de entrada de la API y evitaron exponer las entidades directamente, además de simplificar el cuerpo de las peticiones al recibir categoriaId en lugar de una categoría completa. El CRUD de productos quedó completo y las consultas por relación se resolvieron con métodos derivados de Spring Data, sin escribir SQL. La relación Muchos a Muchos entre Producto y Etiqueta se implementó con @ManyToMany y @JoinTable sobre la tabla intermedia creada en la migración V4. Los dos retos finales confirmaron el comportamiento esperado: eliminar una asociación borra únicamente la fila de producto_etiqueta, y la consulta por etiqueta atraviesa correctamente la relación. Las 17 peticiones de la colección se ejecutan sin errores, con 33 comprobaciones automáticas satisfactorias.
