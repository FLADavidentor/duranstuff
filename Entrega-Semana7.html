Análisis: ¿qué función cumple spring.jpa.hibernate.ddl-auto=validate?

Indica a Hibernate que, al iniciar, compruebe que las tablas y columnas que requieren las entidades existan en el esquema y sean compatibles con ellas. No crea ni modifica nada. Si encuentra una diferencia, la aplicación no arranca. Por eso toda la estructura de la base proviene de las migraciones de Flyway, que se ejecutan antes de que Hibernate valide el modelo. En la sección 7 se demuestra este comportamiento con dos casos reales.

Producto

@Entity
@Table(name = "producto")
public class Producto {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Integer id;

    private String codigo;

    private String nombre;

    @ManyToOne
    @JoinColumn(name = "categoria_id")
    private Categoria categoria;

    @Column(name = "precio_venta")
    private BigDecimal precioVenta;

    private int existencia;

    private String descripcion;

    @ManyToOne
    @JoinColumn(name = "proveedor_id")
    private Proveedor proveedor;

    // Getters y Setters
}

5. Scripts de migración

V1__crear_tablas.sql

CREATE TABLE categoria (
    id SERIAL PRIMARY KEY,
    nombre VARCHAR(100) NOT NULL,
    activa BOOLEAN NOT NULL DEFAULT TRUE
);

CREATE TABLE producto (
    id SERIAL PRIMARY KEY,
    codigo VARCHAR(30) NOT NULL UNIQUE,
    nombre VARCHAR(150) NOT NULL,
    precio_venta NUMERIC(12,2) NOT NULL,
    existencia INTEGER NOT NULL DEFAULT 0,
    categoria_id INTEGER NOT NULL,

    CONSTRAINT fk_producto_categoria
        FOREIGN KEY (categoria_id)
        REFERENCES categoria(id)
);

6. Evidencia de PostgreSQL

Consultas utilizadas como evidencia:

\dt

SELECT version, description, success
FROM flyway_schema_history
ORDER BY installed_rank;

SELECT column_name, data_type
FROM information_schema.columns
WHERE table_name = 'producto'
ORDER BY ordinal_position;

SELECT conname, pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid = 'producto'::regclass AND contype = 'f';
SELECT p.codigo, p.nombre, p.precio_venta, p.existencia,
       c.nombre AS categoria, pr.nombre AS proveedor
FROM producto p
JOIN categoria c ON c.id = p.categoria_id
LEFT JOIN proveedor pr ON pr.id = p.proveedor_id
ORDER BY p.id;

7. Qué hizo Flyway y qué evitó

Esta sección documenta el comportamiento de las migraciones y de ddl-auto=validate mediante casos ejecutados sobre la base de datos.

CasoResultado observado
HIZO · Crear el esquema Sobre una base vacía, V1, V2 y V3 crean las tablas y la relación, y cada versión queda registrada en flyway_schema_history.
EVITÓ · Repetir una migración Al reiniciar, Flyway informa Schema "public" is up to date. No migration necessary. No vuelve a ejecutar V1, V2 ni V3, lo que habría fallado porque las tablas ya existen.
EVITÓ · Alterar el historial Al modificar V1__crear_tablas.sql después de aplicada, el arranque se detiene con Migration checksum mismatch for migration version 1. Impide que el esquema real difiera del historial registrado.
EVITÓ · Trabajar con un esquema atrasado Con una base que no tiene todas las migraciones, validate detiene el arranque indicando la diferencia exacta, en lugar de fallar más tarde durante una consulta.
EVITÓ · Que Hibernate creara tablas Con Flyway desactivado y una base vacía, la aplicación se detiene con Schema validation: missing table [categoria] y la base permanece vacía. Con create o update, Hibernate habría creado el esquema por su cuenta, fuera del control de versiones.

9. Comprobación de aprendizaje

  1. ¿Cuál es la función de Spring Data JPA? Facilitar el acceso a datos sobre JPA. Genera la implementación de los repositorios a partir de interfaces y aporta operaciones de persistencia, consultas derivadas del nombre del método, paginación y ordenamiento. En esta práctica permite guardar y consultar categorías, productos y proveedores sin escribir una clase DAO para cada entidad.
  2. ¿Qué función cumple Hibernate? Es el proveedor de JPA que utiliza la aplicación. Traduce las operaciones sobre entidades Java a sentencias SQL, administra el estado de esas entidades en el contexto de persistencia y convierte los resultados devueltos por PostgreSQL en objetos.
  3. ¿Qué diferencia existe entre JPA y Hibernate? JPA es la especificación: define los contratos y las anotaciones de la persistencia objeto-relacional. Hibernate es una implementación concreta de esa especificación. Las entidades de este proyecto se anotan con jakarta.persistence, que es JPA, y Hibernate es quien ejecuta la persistencia.
  4. ¿Qué función cumple @Entity? Declara que una clase es una entidad persistente administrada por JPA, de modo que sus instancias corresponden a filas de una tabla. Requiere una clave primaria indicada con @Id. @Table permite nombrar la tabla asociada, como categoria, producto o proveedor.
  5. ¿Qué función cumple @ManyToOne? Expresa una relación de muchos a uno. Muchos productos pueden pertenecer a una misma categoría y, tras el reto final, muchos productos pueden pertenecer a un mismo proveedor. El lado @ManyToOne es el propietario de la relación y el que guarda la clave foránea.
  6. ¿Qué función cumple @JoinColumn? Indica cuál es la columna que almacena la clave foránea en la tabla de la entidad propietaria. En Producto, categoria_id referencia categoria(id) y proveedor_id referencia proveedor(id). Las restricciones correspondientes las crean las migraciones V1 y V3.
  7. ¿Qué función cumple JpaRepository? Aporta las operaciones de repositorio para una entidad y el tipo de su identificador, sin necesidad de implementarlas: findAll() lista los registros, findById(id) devuelve un Optional, save(entidad) inserta o actualiza según el estado de la entidad, deleteById(id) elimina, existsById(id) comprueba la existencia y count() devuelve la cantidad de registros.
  8. ¿Por qué se utilizan migraciones? Porque versionan la estructura de la base de datos y permiten reproducir sus cambios siempre en el mismo orden, en cualquier entorno. Flyway registra cada ejecución con su suma de verificación en flyway_schema_history, de modo que una migración ya aplicada no se repite ni se debe editar: los cambios posteriores se agregan en una versión nueva. La sección 7 documenta este comportamiento.
  9. ¿Qué diferencia existe entre V1, V2 y V3? Son tres cambios sucesivos de una misma base de datos, no tres bases distintas. V1 crea categoria y producto con su relación. V2 agrega la columna descripcion a producto. V3 crea proveedor y la columna proveedor_id con su clave foránea. Cada versión aplica únicamente su propio cambio y conserva los datos existentes.
  10. ¿Qué problema puede producir una relación bidireccional al generar JSON? Recursión infinita: el producto serializa su categoría, la categoría serializa su lista de productos y cada producto vuelve a serializar la categoría, hasta desbordar la pila. También puede producir respuestas desproporcionadas al arrastrar colecciones completas. En este proyecto las relaciones son unidireccionales desde Producto, por lo que el problema no se presenta. En un modelo bidireccional se resuelve con DTO, @JsonIgnore, o @JsonManagedReference y @JsonBackReference.

10. Conclusión

La práctica permitió conectar una API REST de Spring Boot con PostgreSQL y resolver la persistencia mediante Spring Data JPA e Hibernate. Las entidades Categoria, Producto y Proveedor representan el modelo del caso de estudio, y las anotaciones @ManyToOne y @JoinColumn trasladan las claves foráneas del esquema al código. Los repositorios que extienden JpaRepository aportaron las operaciones de consulta y guardado sin implementar una sola clase de acceso a datos. Flyway organizó la evolución del esquema en tres versiones aplicadas en orden y registradas en su historial, y las pruebas mostraron que bloquea tanto la repetición de una migración como la modificación de una ya aplicada. Mantener ddl-auto=validate dejó la creación del esquema enteramente en manos de las migraciones y convirtió cualquier diferencia entre el código y la base en un error visible al arrancar. Las pruebas de la API confirmaron que las relaciones quedan persistidas y no solo representadas en el JSON de respuesta.
